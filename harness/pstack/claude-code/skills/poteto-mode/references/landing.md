# Landing through the repository's release procedure

**A merge that triggers release work is a release. When the target repository has a release procedure, landing a PR means running that procedure, not `gh pr merge`.**

1. **Find the procedure before the first merge.** Look in the target checkout's `AGENTS.md`, its release runbooks, and the host's skills for one that merges and releases a reviewed PR (for example a `merge-and-release` skill). Record which one you found, or that there is none. With none, the playbook's own merge step stands.
2. **The procedure owns the merge.** It replaces the playbook's `gh pr merge` call and GitHub auto-merge. Never arm `--auto` on a PR whose merge triggers release work, because auto-merge lands the PR with nobody running the release steps after it. The playbook's verdict gate still comes first: the procedure's "reviewed PR" is a PR whose verdict covers its current head.
3. **Meet its pre-merge criteria at merge-ready.** Merge-ready means the procedure would accept the PR now: review and verdict cover the current head, required checks are green or covered by local evidence the procedure explicitly permits for that check, the PR is mergeable under branch protection, and no blocking finding is open. A check the procedure's fallback covers counts as the green CI a playbook waits for, within that fallback's limits and with its evidence recorded (commit SHA, commands, results). It never turns the hosted check green, and it never bypasses an enforced check.
4. **List the release work at merge-ready.** From the PR's full diff against its base, list every category the procedure names (for example migrations, services and workers, environment variables, verification), including the ones that need no action, with the evidence for each. Resolve a known missing prerequisite that would break an automatic deployment before the merge. Do not perform any release step during babysit or build.
5. **Authorization follows the procedure, not the playbook.** A grant to merge does not grant production database or infrastructure writes. Production release steps run only when the operator's grant names the release environment. Without that grant, merge only if the procedure allows merging without releasing, then stop at merged and hand the release action list to the operator. This is the deploy pause in poteto-mode's Autonomy section.
6. **Release one PR at a time.** Releases share databases, workers, and configuration, so the root serializes them even when owners build in parallel. An owner whose PR is merge-ready queues for release with the root, and the root starts the next release only after the previous one reports verified or blocked.
7. **Report merged, deployed, and verified separately.** A PR is landed when the procedure reports it verified. Merged-but-unreleased, deployed-but-unverified, and blocked are separate states, each with the procedure's evidence: the merge commit, migration versions and target, deployed revisions, variable names without values, and the smoke check.
